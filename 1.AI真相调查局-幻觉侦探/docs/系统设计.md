- 文档版本：v0.3（已按架构师、研发工程师、独立二次评审三轮修订）
- 日期：2026-11-15
- 状态：待确认
- 上游依据：《AI真相调查局-幻觉侦探研发任务书.md》（GDD）、《长期规划.md》

> 本文件是首款游戏的**整体设计**：系统架构 + 功能模块 + 详细设计。它不写实现代码，只定义"做什么、怎么分模块、数据长什么样、状态怎么流转、分数怎么算、进度怎么存"。各阶段进入开发前的更细实现拆分，放到 `docs/stages/` 下对应阶段的详细设计文档里。

## 1. 设计意图与目标

### 1.1 意图

玩家扮演虚构 AI 事实调查机构（AI 真相调查局）的调查员，审查 AI 助手 ORION 生成的报告：逐条判断陈述是否有证据支持、证据是否矛盾、是否缺乏证据、是否已过时，并给出最终处理建议。核心认知体验是让玩家亲自发现——**看起来确定、专业的 AI 答案，也可能缺乏证据、引用不存在、引用过时，或从真实数据里做出错误推断**。

### 1.2 目标

1. 数据驱动，多案件复用同一套核心机制（新增案件只加数据，不改核心代码）。
2. 核心判定逻辑（陈述判定、证据关联、评分、状态转换）**纯函数化、可单元测试**。
3. 案件内容（JSON）与游戏逻辑完全分离。
4. 本地单机、零后台、零实时 LLM API、零账号、零联网。
5. 复盘必须清晰区分"模型错误 / 幻觉 / 证据不足 / 过时信息"，不得把拟人化角色行为说成模型有意识或故意欺骗。
6. 玩家完成案件后获得知识卡、图鉴条目与调查员称号（§7）。

### 1.3 非目标（本设计不包含）

在线多人、排行榜、账号、云存档、Steam Cloud/Achievements；实时 LLM 生成；付费道具/商城/提示收费；关卡编辑器、UGC、社区；让玩家自由切分报告的完整"段落编辑器"（见 §5.4 的取舍）。

### 1.4 反目标（做出来就算失败）

变成"AI 知识选择题"或"AI 课程"；靠背答案或猜颜色拿高分；把"没找到证据"等同于"事实为假"；内容事实不准确；把游戏简化模型说成真实系统实现；用"全选未证实"这类偷懒策略也能拿高分。

## 2. 硬约束

1. 不实现服务器 / 后端 / 云数据库 / 账号系统。
2. 不调用实时大模型 API，客户端不放任何 API Key。
3. 默认构建不含 Steamworks，核心玩法不依赖它；Steam Cloud/成就属**可选、非必需**的发行例外，接入前单独做隐私评估并经负责人批准（发行候选阶段只评估是否接入）。
4. 不做多人联机；不引入付费道具。
5. 不执行用户任意代码，不用 eval 解析案件数据，不把 JSON 当代码。
6. 不向外部网络发送数据；核心构建中出现任何网络 API（`HTTPRequest`/`WebSocketPeer`/`OS.shell_open`/Steam 调用）即视为违规（§13 有静态扫描测试）。
7. 素材/文案记录来源与授权（`ASSET_LICENSES.md` / `CONTENT_SOURCES.md`）。
8. 技术栈锁定：Godot 4.7 最新稳定补丁 + GDScript（开发开始时核实并固定版本，不用 beta）。
9. 测试零第三方依赖（§13），不擅自引入 GdUnit4/GUT 等框架。

## 3. 总体架构

### 3.1 分层与依赖规则

四类职责，依赖方向单向：

```
Presentation（scenes/**）
      │  只读值对象 + 调 GameFlow 发起变更
      ▼
GameFlow（应用编排：路由/守卫/会话/进度落盘）
      │
      ▼
Domain（纯逻辑：CaseDefinition/CaseSession/Scorer/CaseResult/枚举与目录）
      ▲              ▲
      │              │
ContentLoader       SaveManager
（读 JSON 建定义）   （读写存档与设置）
```

- **Domain** 是纯逻辑层：不依赖引擎场景、不做文件 I/O、不发信号、不引用 autoload。
- **ContentLoader**（infrastructure）：读 `content/**/*.json` → `CaseDefinition` + `CaseCatalog` + 知识卡/称号目录；校验失败返回错误，绝不返回半成品。
- **SaveManager**（persistence）：读写 `user://` 存档；只依赖 Domain 的 DTO，由 GameFlow 调用，不反向依赖 GameFlow。
- **GameFlow**：唯一持有当前 `CaseSession`/`CaseResult`；编排"加载→简报→调查→评分→落盘"；按状态守卫页面导航。
- **Presentation**：可读 Domain 只读值对象，但所有 mutation 必须经 GameFlow；`scenes/` 禁止直接调用 `CaseSession.judge_claim/link_evidence/submit_final/use_hint`，禁止直接读写文件。

### 3.2 Autoload（3 个，顺序固定）

| 顺序 | 单例 | 职责 |
|---|---|---|
| 1 | `SaveManager` | 存档/设置唯一写者：`load() -> PlayerProgress`、`save(progress)`、`get_setting/set_setting`、原子写 + 迁移 |
| 2 | `ContentLoader` | `load_case(id) -> CaseLoadResult`、`get_catalog()`、`get_knowledge_cards()`、`get_titles()` |
| 3 | `GameFlow` | 应用编排：`start_case(id)`、`goto(page)`、`end_case()`、mutation 转发 + 状态守卫、当前 session/result 缓存 |

Autoload 顺序写入 `project.godot`。**无 EventBus、无独立 Settings**：全局信号用 GameFlow 具名信号（`case_started / case_state_changed / case_submitted / case_completed`），页面 `_ready` 连接、`_exit_tree` 断开；设置并入 SaveManager。

### 3.3 页面与导航

每页一场景 + `change_scene_to_file`；页面无持久状态。`goto` 用 `Page` 枚举 + `PAGE_SCENES` 常量表，校验"phase → 允许页面"。

| 页面 | 场景 |
|---|---|
| 主菜单 | `scenes/menu/main_menu.tscn` |
| 案件选择 | `scenes/case_select/case_select.tscn` |
| 案件简报 | `scenes/briefing/briefing.tscn` |
| 调查桌面（核心） | `scenes/investigation/investigation_desk.tscn` |
| 最终结论 | `scenes/verdict/final_verdict.tscn` |
| 结果与评分 | `scenes/debrief/results.tscn` |
| 知识复盘 | `scenes/debrief/debrief.tscn` |
| 图鉴与成就 | `scenes/knowledge/collection.tscn` |
| 设置 | `scenes/settings/settings.tscn` |

证据查看器是调查桌面内叠加层（§5.5），不是页面。设置页返回用 `previous_page` 栈。

### 3.4 数据流

```
ContentLoader 读 content/cases/*.json + index.json → 校验 → CaseDefinition + CaseCatalog
GameFlow.start_case(id) → 构造 CaseSession（phase NOT_STARTED → BRIEFING）
Briefing → begin_investigation（→ INVESTIGATING）
InvestigationDesk（读 CaseSession，经 GameFlow 改判）
  → 每条 claim judge_claim(label) + link_evidence(ids)
  → 全判完 → READY_TO_SUBMIT
FinalVerdict → submit_final(action)（→ SUBMITTED，GameFlow 调 Scorer → 缓存 CaseResult）
Results（只读 CaseResult 总分，不暴露逐条对错）
Debrief → begin_debrief（→ COMPLETED）→ 更新 progress/知识卡/称号 → SaveManager.save
```

## 4. 领域模型与数据设计

### 4.1 枚举（`scripts/domain/enums.gd` 集中映射，未知字符串一律校验错误）

| 枚举 | 取值 |
|---|---|
| `ClaimLabel` | `supported / contradicted / unverified / outdated`（封闭集合） |
| `FinalAction` | `approve / approve_with_caveat / hold / revise`（固定 4 个） |
| `ClaimKind` | `fact / calculation / inference`（§6 元数据，用于复盘与内容分析，不计分） |
| `ReasoningPattern` | `correlation / causation / subset_vs_total / other` |
| `SourceType` | `primary_record / official_announcement / internal_note / report / dataset / other` |
| `Reliability` | `high / medium / low` |
| `Difficulty` | `easy / medium / hard` |
| `HintType` | `direction / evidence / concept` |
| `ContentFormat` | `text / table` |

### 4.2 判定目录 `ClaimLabelCatalog`（单一来源）

`label → {display_name, icon, color, shortcut, definition, example}`，供调查桌面按钮、常驻 glossary、复盘、图鉴共用。新增类别只改这里 + §4.1 + §9 矩阵。

### 4.3 核心类型

| 类型 | 基类 | 职责 |
|---|---|---|
| `CaseDefinition` | RefCounted | 一案完整定义；只由 ContentLoader 构造，约定只读 |
| `ClaimDefinition` | 内嵌 | 陈述（文本、正确标注、解释、claim_kind、关键/相关证据） |
| `EvidenceDefinition` | 内嵌 | 证据（元信息 + 正文 + 可靠度依据 + 与 claim 的 relation） |
| `CaseSession` | RefCounted | 运行时状态：判定、证据关联、提示、最终动作、`phase` 状态机 |
| `CaseResult` | RefCounted | 评分结果（§9.5 字段表） |
| `PlayerProgress` | 存档 DTO | 案件完成/最高分、知识卡、称号、最后案件 |
| `Scorer` | 静态纯函数 | `score(session, case_def) -> CaseResult` |
| `CaseCatalog` | RefCounted | 案件清单（`index.json`） |

`CaseDefinition` 用 RefCounted（非 Resource）；"不可变"靠只暴露 getter；加载时构建 `claims_by_id`/`evidence_by_id` 字典。

### 4.4 CaseSession 关键方法（示意）

```
new(case_def)                       # 建 id→index 字典，phase=NOT_STARTED
query: get_judgement(claim_id), is_judged(claim_id), all_claims_judged(), phase
mutation（仅 GameFlow 调用）:
  judge_claim(claim_id, label) -> bool      # 覆盖式改判；未知 id/label 返回 false
  link_evidence(claim_id, evidence_id) -> bool
  unlink_evidence(claim_id, evidence_id) -> bool
  use_hint(hint_id) -> bool                  # 每案至多 1 次
  submit_final(action) -> bool               # 仅 READY_TO_SUBMIT；幂等
  reset()
  to_dict() -> Dictionary                    # 草稿存档：序列化判定/关联/提示/phase
  from_dict(dict) -> bool                    # 恢复草稿（校验字段）
```

`all_claims_judged()` 以 `CaseDefinition.claims` 为基准比对。

## 5. 功能模块设计

### 5.1 主菜单
导航到案件选择 / 图鉴 / 设置 / 退出；显示本地进度摘要；常驻"虚构案例 · 非真实模型测评"footer。

### 5.2 案件选择
读 `CaseCatalog` + `PlayerProgress`，列出案件（含锁定/完成/最高分）。解锁由 catalog `unlock_condition` + progress 派生，不落盘 `unlocked`。

### 5.3 案件简报
展示背景、目标列表、`case.as_of`（调查基准时间）；案件 01 前先过 60–90 秒**互动校准**（§5.12）。

### 5.4 调查桌面（核心）
- 四区域：左（目标/进度/glossary）、中（报告 + 内嵌陈述）、右（证据列表）、底（当前陈述判定 + 证据关联）。
- **报告渲染为连续文档**：`report.segments` 的 narration 与 claim 交替，claim 语句作为报告的一部分内联显示（可点击聚焦判定），**不折叠其他陈述、不做独立的 claim 卡片列表**——保留"在一份看似可信的报告里发现这句话有问题"的 agency。
- 玩家可点击报告中的句子聚焦到对应陈述；可主动标记关键词（标记用于高亮/筛选证据，本地 UI 状态，不进存档）。
- 报告区域顶部/左侧有"陈述导航器（progress pips）"：每条 claim 一个圆点（已判/未判），点击平滑滚动定位到对应内联句子，避免漏判。
- 证据列表可排序/筛选。所有 mutation 经 GameFlow；未全判完"提交结论"灰显。
- 调查阶段不展示任何答案字段（`correct_label`、`related_evidence_ids`、`key_evidence_ids`、证据 relation），仅复盘显示。

### 5.5 证据查看器（叠加层）
调查桌面内 `CanvasLayer + PopupPanel`；`open(evidence_id)` / `evidence_link_requested(evidence_id)`。展示标题、来源类型、创建/生效时间、可靠度 + `reliability_basis`、是否一手、正文（text/table）；不展示 `related_claim_ids`。

### 5.6 最终结论
输入 `final_decisions.actions[]`（动作描述，**不展示权重**）；输出 `GameFlow.submit_final(action)`；仅 `READY_TO_SUBMIT` 可进。

### 5.7 结果与评分（Results）
**只展示总分、三项分项、提示扣分、最终动作结果 + "查看复盘"主 CTA**。不展示逐条对错与 `correct_label`（把揭晓留给复盘，保住 aha）。

### 5.8 知识复盘（Debrief，强制揭晓节奏）
- **逐条揭晓**：先展示玩家判断 + 证据链，再揭晓正确 label + 解释（保留 aha）。
- 展示正确判定、关键证据、玩家差异、AI 知识点、可迁移检查建议。
- **迁移题交互化**：先提交答案，再揭晓参考答案（不计分）。
- 知识卡与称号在 Debrief 结束时发放；"completed" = 已看完 Debrief。未看 Debrief 时"下一案/返回"需确认。

### 5.9 图鉴与成就（Collection）
已收集知识卡（含适用范围/依据）、已获称号、未解锁预览（**锁定卡只显示剪影/分类，不显示标题正文，防剧透**）；见 §7。

### 5.10 设置
音量、字体缩放、窗口模式、退出；含"清除本地进度"按钮 + 隐私/离线说明（无账号、无网络、无遥测、存档仅本地 `user://`）。

### 5.11 帮助
调查桌面内抽屉：四类判定含义、评分规则、操作方式、证据关联占分说明。

### 5.12 教程与 onboarding（案件 01 内建）
1. 案件 01 前 60–90 秒互动校准：一条样例陈述 + 两张证据卡，玩家先选，再解释为什么。
2. 案件 01 第一条 claim 引导式：锁定其他 claim，四类按钮带一句话定义，选后给"为什么"反馈。
3. 调查桌面常驻 glossary 一行（用例子讲清 `unverified` vs `contradicted`、`outdated` vs `contradicted`）。
4. 首次证据关联给 coach mark。
5. 每案内容/节奏预算（claim 数 3–5、证据数 5–8、正文字数、目标 10–20 分钟）写入案件内容，S2 用 5–10 名目标用户无开发者指导试玩验证。

## 6. 案件内容 Schema（v2）

### 6.1 案件清单 `content/cases/index.json`

```json
{
  "schema_version": 2,
  "cases": [
    { "case_id": "case_001", "title": "不存在的引用", "difficulty": "easy", "order": 1,
      "unlock_condition": "always", "summary": "……" },
    { "case_id": "case_002", "title": "过期的真相", "difficulty": "easy", "order": 2,
      "unlock_condition": "prev_case_completed", "summary": "……" }
  ]
}
```

### 6.2 案件文件 `content/cases/case_001.json`


**关键约定：**
- `report.segments` 是报告唯一真源；claim 文本只存 `claims[].text`，报告用 `claim_id` 引用；UI 渲染为连续文档、claim 内联。
- 证据关联**只保留 claim 侧为权威**：`key_evidence_ids ⊆ related_evidence_ids`；evidence 侧 `relations[]` 为内容校验/复盘元数据（`supports / contradicts / context / checked_no_match`），不向玩家展示。
- `key_evidence_ids` = 判定该 claim 必须考虑的证据；`related_evidence_ids` = 相关可关联（含 key）。
- **时间模型**：`created_at`（记录产生时间）、`valid_from/valid_until`（事实适用期，null 表无限）、`as_of`（调查基准）。`outdated` 成立需"所依赖来源 `valid_until < as_of`，且无 `valid_from <= as_of` 的新来源支持它"；`valid_from > as_of` 的来源是"已宣布未生效"，不得当当前资料；快照类证据（`record_type: snapshot`）必须给 `valid_until`。
- `claim_kind`（fact/calculation/inference）+ `reasoning_pattern` 供案件 03 的复盘/内容分析使用，不直接计分。
- `final_decisions` 用 `preferred_action` + `accepted_actions`（每个带 `score_weight` + `reason`），允许两可案件多个动作接近满分，避免"唯一强制正确措辞"。
- `fiction_note`/`model_behavior_note` 为玩家可见的虚构声明与模型行为边界说明。

### 6.3 加载校验（ContentLoader，返回 `CaseLoadResult {ok, case_def, errors}`，不抛异常）

- 所有 id 唯一；`claims` 数量 3–5；`key_evidence_ids ⊆ related_evidence_ids` 且 key 非空、引用存在。
- `correct_label / claim_kind / reasoning_pattern / source_type / reliability / difficulty / hint.type / content_format / record_type / relation` 属合法枚举。
- 日期 ISO；`valid_from <= valid_until`。
- **`outdated` 硬规则**：每条 `correct_label == outdated` 的 claim 至少有一条 key evidence 满足 `valid_until < as_of`；否则拒绝加载。
- `preferred_action` 必须在 `accepted_actions` 中；至少一个动作 `score_weight == 1.0`；`score_weight ∈ [0,1]`。
- `report.segments` 中 claim 片段引用存在，每条 claim 至少被引用一次。
- `fiction_note`、`model_behavior_note`、`reliability_basis`、explanation 非空。
- 知识解释正文禁含"故意/撒谎/意识/想骗/欺骗"等拟人化意图词（内容 lint）。
- JSON 用 `JSON.new().parse()` 取错误行号；数字按 float；重复 key 靠内容规范避免。

## 8. 游戏流程与状态机

### 8.1 单一所有者

状态机逻辑在 Domain（`CaseSession.phase + transition`，可单测）；运行时唯一持有者是 GameFlow（构造/持有 session、调 transition、路由页面、守卫、触发评分与落盘）。

### 8.2 状态与转移表

| 当前 phase | 事件/动作 | 新 phase | 守卫 | 副作用 |
|---|---|---|---|---|
| NOT_STARTED | `start_case(id)` | BRIEFING | case 加载成功 | GameFlow 持有 session |
| BRIEFING | `begin_investigation` | INVESTIGATING | 无 | — |
| INVESTIGATING | `judge_claim / link_evidence / unlink_evidence / use_hint` | INVESTIGATING | 参数合法 | 覆盖式更新 |
| INVESTIGATING | （`all_claims_judged()` 为真） | READY_TO_SUBMIT | 全判完 | 自动 |
| READY_TO_SUBMIT | `judge_claim`（改判） | READY_TO_SUBMIT | 允许改判 | — |
| READY_TO_SUBMIT | `submit_final(action)` | SUBMITTED | action 合法 | 幂等；GameFlow 调 Scorer → 缓存 CaseResult |
| SUBMITTED | `begin_debrief()`（进入复盘） | COMPLETED | — | 更新 progress/知识卡/称号 → 落盘（"完成"=已看复盘） |
| INVESTIGATING / READY_TO_SUBMIT / SUBMITTED / COMPLETED | `reset()` | INVESTIGATING | — | 清空判定/关联/提示/最终动作/结果/phase |
| 任意 | `end_case()` | — | — | 清空 GameFlow 持有的 session/result 引用 |

守卫：`submit_final` 仅 `READY_TO_SUBMIT` 且 action 合法；幂等。`judge_claim` 覆盖式改判。零 claims 是内容校验错误。

### 8.3 状态 → 允许页面

| phase | 允许页面 |
|---|---|
| BRIEFING | briefing |
| INVESTIGATING / READY_TO_SUBMIT | investigation_desk |
| READY_TO_SUBMIT | final_verdict |
| SUBMITTED | results |
| COMPLETED | debrief |
| 任意 | settings、case_select、collection、main_menu |

页面序列固定：FinalVerdict → Results → Debrief → CaseSelect/NextCase。`goto` 入口校验该表，非法跳转返回错误并记录。Results→Debrief 由"查看复盘"触发 `begin_debrief`。

## 9. 评分系统详细设计

纯函数 `Scorer.score(session, case_def) -> CaseResult`。每案满分 100 = **判定准确度 60 + 证据关联 30 + 最终建议 10**，再叠加提示上限。内部全 float，仅最终显示四舍五入（round half up）到 int。

> v0.3：删除独立的"不确定性校准 15 分"（与判定矩阵重复奖励同一答案，是"全 unverified 套利"的来源）；"奖励谨慎、惩罚无据断言"改由不对称矩阵直接承担。

### 9.1 判定准确度（60 分）— 4×4 不对称常量矩阵

每条 claim 满分 `60 / n_claims`，乘矩阵系数。矩阵为唯一真源（`scoring_matrix.gd` 常量 + 启动断言覆盖 16 格）：

| correct \ player | supported | contradicted | unverified | outdated |
|---|---|---|---|---|
| **supported** | 1.00 | 0.00 | 0.50 | 0.00 |
| **contradicted** | 0.00 | 1.00 | 0.50 | 0.00 |
| **unverified** | 0.00 | 0.00 | 1.00 | 0.00 |
| **outdated** | 0.00 | 0.00 | 0.50 | 1.00 |

规则（教学优先级）：精确一致 1.00；**把"缺乏证据"断言成任何明确结论（supported/contradicted/outdated）→ 0.00**（核心教训"没有证据≠为假"）；把"本该是明确结论"的陈述谨慎判成 unverified → 0.50（态度对、漏证据）；其余错误断言 → 0.00。

### 9.2 证据关联质量（30 分）

只统计判定阶段玩家主动关联的证据；`related_evidence_ids` 不提前展示。每条 claim：

```
key_count = |key_evidence_ids|
hit       = |player_linked ∩ key_evidence_ids|
miss      = |key_evidence_ids \ player_linked|
unrelated = |player_linked \ related_evidence_ids|          # 只惩罚明显无关证据
claim_raw = clamp(hit - λ·min(unrelated, key_count) - μ·miss, 0, key_count)   # λ=μ=1；unrelated 惩罚封顶，不让一条额外关联抹掉关键命中
```

全局：`evidence = 30 × Σ claim_raw / Σ key_count`，clamp 到 [0, 30]。提交前 UI 显示"已关联证据 n/N"摘要，对未关联证据的陈述给软警告（证据关联占 30 分）。

### 9.3 最终处理建议（10 分）

- `chosen == preferred_action` → 10。
- 否则 `chosen` 在 `accepted_actions` 中且 `score_weight == w` → `10·w`（两可案件允许多个动作接近满分）。
- 否则 → 0。
- UI 只展示动作描述，不展示权重；复盘不仅解释"为什么这个更优"，也解释"备选动作为何能拿部分分"（如"虽然最佳是退回修订，但暂缓发布也是基于风险防范的合理决策"），不把单一动作框定为唯一正确。

### 9.4 提示上限

每案 3 条提示，玩家免费任选 1 条（`use_hint` 每案至多 1 次）。

```
cap = 100 - 5 × |hints_used|
total = round(min(earned, cap))
hint_penalty = earned - min(earned, cap)
```

### 9.5 CaseResult 字段表

```
CaseResult:
  total: int, earned: float,
  breakdown: { accuracy, evidence, final_action },
  hint_penalty: float,
  claims: Array[ClaimResult],
  final_action_detail: { chosen, preferred, weight, points }
ClaimResult:
  claim_id, player_label, correct_label, matched, points, max_points,
  key_hit_ids, key_missed_ids, unrelated_ids
```

### 9.6 反刷分不变量（§13 断言依据）

- 满分恒等于 100（无提示）。
- "正确答案" > "3/4 正确 + 证据" > "全 unverified + 全 key 证据" > "乱选"。
- "全 unverified + 全 key 证据 + 正确最终动作" **必须 < 60**（上限断言）。
- 使用提示后严格低于未提示。

## 10. 本地存档设计

- 位置 `user://`；JSON；单一 `save_version`；`unlocked` 由 progress + catalog 规则派生，不落盘。

```json
{
  "save_version": 2,
  "settings": { "volume_master": 0.8, "volume_music": 0.6, "font_scale": 1.0, "window_mode": "windowed" },
  "progress": { "case_001": { "completed": true, "best_score": 87 } },
  "collected_cards": ["card_fc_001"],
  "earned_titles": ["title_intern"],
  "last_case_id": "case_001"
}
```

- **唯一写者 SaveManager**；原子写（`save.tmp` → rename）+ 保留 `save.bak`。
- **迁移** `migrate_v1_to_v2`；读到高于当前版本的存档 → 拒绝写入并提示，不覆盖（防降级清档）。
- 损坏/不兼容：保留原文件 + 记录日志 + 回退默认值，游戏仍可启动。
- 写入时机：案件提交成功、进入 COMPLETED、返回案件选择、退出；判定过程不写。`best_score = max(old, new)`。
- **日志最小化**：仅本地、不写 save 内容/系统用户名/完整路径、限制大小并轮转，release 关闭。
- 设置 debounce flush；值做范围/枚举校验。`last_case_id` 用于案件选择高亮"上次玩的案件"（若未实现则删除此字段）。
- 测试：SaveManager 接受路径注入，不碰真实 `user://`。

### 草稿存档（Draft / 崩溃恢复）

- `CaseSession.to_dict()/from_dict()` 序列化当前判定、证据关联、提示、最终动作、`phase`（不含设置、不含案件定义）。
- 调查中每次 `judge_claim / link_evidence` 后，GameFlow 以 debounce（0.5–1s）把 session 草稿原子写入 `user://draft.json`（独立于正式 `save.json`）。
- 启动时若存在未完成草稿，主菜单/案件选择显示"继续上次调查"；玩家选择后 `from_dict` 恢复并回到调查桌面；开始新案或完成案件则清除草稿。
- 草稿遵守同样的最小化与日志边界（不含个人信息）。

- 方向：**调查卷宗 / 数字档案室**——纸质档案 + 数字终端混合，温和悬疑，不恐怖、不科幻发光。
- 颜色 token（变量，S3 定值）：`color.bg`（冷灰蓝底）、`color.surface`（档案卡面）、`color.ink`（正文）、`color.accent`（单一强调色）、`color.danger`（矛盾）、`color.warning`（过时/未证实）。
- 字体：可商用 CJK 字体 + 西文配对；禁止默认字体栈；正文 ≥16px。
- 间距 4px scale（4/8/12/16/24/32）。
- 反 AI 味护栏：不用紫蓝渐变/发光/霓虹；不用三列 icon-in-circle 卡片网格；不用 emoji 当图标；卡片只在"卡片即交互"时用；不用居中堆叠 hero。
- 状态不只靠颜色：矛盾/未证实/过时各有图标 + 文字。
- 常驻 footer/badge："虚构案例 · 非真实模型测评"（主菜单/简报/调查/证据/复盘）。

### 11.5 无障碍与响应式

- 1280×720 基础 + 窗口缩放 + 16:9；鼠标为主，键盘辅助（Tab 遍历、数字/方向键判定）。
- 键盘可 Tab 到达，焦点可见；对比度正文 ≥4.5:1；热区 ≥44px。
- 术语首次出现给解释（glossary 常驻 + 帮助抽屉）。

### 11.6 术语 glossary（常驻）

- **有证据支持**：可靠证据足以支持该陈述。
- **证据矛盾**：可靠证据与陈述直接冲突（从一开始就冲突）。
- **缺乏证据**：现有资料不足以确认、也不足以证伪——**不是"假的"**。
- **信息过时**：曾经正确，但已被新资料取代。
- **幻觉**（游戏语境）：模型生成与事实/来源不符的内容，不表示模型有感知或意图。

## 12. 内容生产规范与校验

内容生产（S4）遵守《研发任务书》第 12 节，并满足：

1. 先定目标知识点与认知转变，再写 AI 报告（`report.segments`）。
2. 先设计答案与证据，再倒推报告。
3. 逐条证据检查支持/反驳/无法判断；`outdated` 必须有时间链；`contradicted` 依赖"完整覆盖"的证据要写清 `reliability_basis` 覆盖范围。
4. 不把"没有记录"当"绝对没发生"，除非证据系统明确完整覆盖。
5. 时间、编号、人物、地点、文件一致。
6. 每个误判点写 explanation。
7. 每案 4 组评分 fixture（全对 / 部分对 / 全 unverified / 谨慎未证实），每组带期望分数区间。
8. 迁移题检查理解（交互式，不计分）。
9. 所有虚构内容标记虚构（`fiction_note`）；知识解释禁含拟人化意图词；知识卡必有 `scope`/`references`/`last_reviewed`。

**内容质量门禁（test_content_quality.gd）**：案件 01 必须同时有 `contradicted` 与 `unverified`；案件 02 必须有 `outdated` 且时间链成立；案件 03 必须有 supported 计算 + contradicted/unverified 推断；每张知识卡有 scope/来源；每案有 `fiction_note`；不引用真实机构/logo。

所有内容进正式版前经负责人审核；`CONTENT_SOURCES.md` 记录知识依据与事实边界。

## 15. 技术决策记录（Approaches）

- 内容承载：数据驱动 JSON + 通用引擎（选定）；否决每案硬编码、第三方叙事框架。
- 技术栈：Godot 4.7 稳定补丁 + GDScript（GDD 已定）。
- 页面导航：每页一场景 + `change_scene_to_file`；EvidenceViewer 用叠加层。
- 状态机：逻辑下沉 Domain，GameFlow 单持有 + 路由；SUBMITTED 只服务 Results，进入 Debrief 才 COMPLETED。
- 事件：无 EventBus，用 GameFlow 具名信号。
- Autoload：3 个（GameFlow/ContentLoader/SaveManager）。
- CaseDefinition：RefCounted，约定只读。
- 测试：零依赖 headless 脚本。
- 评分：60/30/10 + 不对称矩阵（"奖励谨慎、惩罚无据断言"由矩阵承担，不设独立校准分）。
- 报告呈现：连续文档 + 内嵌陈述（保留"发现"agency），不做独立 claim 卡片列表、不做玩家自由切分报告。
