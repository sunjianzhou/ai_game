# S5 封闭测试与修正 详细设计

- 文档版本：v0.1（待确认）
- 日期：2026-11-19
- 上游依据：`阶段规划路线.md`（S5）、`AI真相调查局-幻觉侦探研发任务书.md`（Milestone 4）、`长期规划.md`（Phase 4）
- 状态：进行中

> S5 = GDD Milestone 4（封闭测试与修正）。S1–S4 已把三案完整可玩，S5 是**测试运营 + 修复**：准备测试材料、招募玩家试玩、收集反馈、分类修复、回归。这个阶段依赖真实玩家，我负责准备材料 + 修复，招募与执行需要你配合。

---

## 1. 目标与验收标准

**目标**：用真实目标用户试玩验证核心玩法是否好玩、是否好懂，发现并修复崩溃/判分/文案/卡点问题。

**验收标准（全部满足才进 S6）**：
1. 至少 10 名目标用户（条件允许扩到 30+）独立完成至少一案的试玩。
2. 收集到：开始率、每案完成率、每案耗时、错误判定类型、复盘理解度、是否愿意继续下一案。
3. 崩溃/判分错误/文案歧义/卡点 四类问题被记录、分类、修复（或明确标注"已知限制"）。
4. 修复后回归测试全绿（14 个测试文件）。

---

## 2. 测试材料

### 2.1 测试版 Build
- Windows `.exe`（`build/windows/`），含三案；无需安装、解压即玩。
- 版本号标注（如 v0.4-alpha），便于反馈定位。

### 2.2 测试说明（给玩家）
- 一句话玩法说明 + 四类判定含义 + 操作步骤（点陈述→判定→关联证据→提交）。
- 明确"这是虚构案件、非真实模型测评"。
- 说明测试目的（找问题，不是考核）。

### 2.3 反馈表（给玩家）
- 基础：第几案、是否完成、耗时、是否用了提示。
- 体验：哪里卡住/看不懂、哪条判定让你困惑、四类判定是否分得清。
- 结论：是否愿意继续下一案、最想改进的一点。

---

## 3. 招募与执行

- 招募渠道：目标用户（用过 DeepSeek/豆包/ChatGPT 等、对 AI 好奇、非开发者优先）。
- 执行方式：玩家独立试玩（无开发者指导），录屏或口头反馈可选。
- 样本：先 5–10 人小样本迭代，再扩到 30+。

---

## 4. 数据收集指标

| 指标 | 用途 |
|---|---|
| 开始率 / 完成率 | 是否愿意玩、是否玩得下去 |
| 每案耗时 | 是否在 10–20 分钟 |
| 错误判定类型（尤其 unverified vs contradicted、outdated vs contradicted 混淆） | 教学是否成立 |
| 复盘理解度（迁移题对错） | 是否真学到知识点 |
| 是否愿意继续下一案 | 核心乐趣是否成立 |
| 卡点 / 崩溃 / 文案歧义 | 修复清单 |

---

## 5. 问题分类与修复流程

| 类别 | 示例 | 优先级 |
|---|---|---|
| 崩溃/阻塞 | 崩溃、卡死、无法继续 | P0 |
| 判分错误 | 分数算错、满分不可达、套利 | P0 |
| 文案歧义 | 判定/动作/复盘看不懂 | P1 |
| 卡点 | 不知道下一步、UI 不反馈 | P1 |
| 体验建议 | 视觉/音效/节奏 | P2 |

流程：记录 → 分类 → 优先级排序 → 修复（TDD，先写复现测试）→ 回归全绿 → 记录到 TEST_PLAN。

---

## 6. 回归测试

每次修复后跑 `godot --headless --path . -s res://tests/run_tests.gd`，确认 14 个测试文件全绿。

---

## 7. 待定与留给开发者的决策

1. 测试版是否加"开发者反馈上报"（离线日志/本地问题记录），还是纯靠玩家口头/文字反馈。
2. 是否需要录屏观察（首 3 名玩家建议录屏，观察卡点）。
3. 已知限制清单（如"音效占位""动态背景未做"）是否在测试说明里提前告知玩家，避免误报。
