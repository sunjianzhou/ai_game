## 1. 目标与验收标准

**目标**：跑通核心玩法闭环——玩家从主菜单进入案件 01，读简报 → 读 ORION 报告 → 判断 3 条陈述 → 关联证据 → 提交最终建议 → 看评分 → 复盘，全程无需开发者指导。

**验收标准（全部满足才进 S3）**：
1. 无开发者指导的测试者能独立完成案件 01（10–20 分钟）。
2. 不同答案组合的分数符合 §13 评分规格（`test_scoring.gd` 表驱动 + 精确期望值全绿）。
3. 判定逻辑可自动测试：`godot --headless --path . -s res://tests/run_tests.gd` 退出码 0。
4. 案件 01 内容通过 schema v2 全量校验（含每类错误一个负例 fixture）。
5. 案件 01 正确教学 `unverified` vs `contradicted` 的区分（`test_content_quality.gd`）。

## 4. GDScript 类型约定（先定死，避免实现时踩坑）

- **可空字段用 `Variant`**：JSON 的 `null` 不能赋给 `String`/`Dictionary` 类型注解。`valid_from`/`valid_until`/`reasoning_pattern` 用 `Variant`（null 表无限早/晚/无）。
- **`table` 默认 `{}`**：`content_format == "table"` 时才用；读取时 `if v == null: v = {}`。
- **typed array 逐元素构造**：`JSON.parse` 返回 untyped `Array`，赋给 `Array[String]` 会报错。用 `for x in raw: if typeof(x) == TYPE_STRING: arr.append(x)` 构造。
- **JSON 数字是 float**：`order: int` 要 `int(d.get("order", 0))`。
- **枚举辅助用命名的字典/方法**（不用 `to_string`/`from_string`，避免与 `Object.to_string` 冲突）：`claim_label_name(v: int) -> String`、`claim_label_value(s: String) -> int`（未知返回 -1）。9 个枚举各自一对。

## 5. 领域模型（`scripts/domain/`，全部 RefCounted、纯逻辑）

### 5.1 定义类型

```gdscript
class_name ClaimDefinition
extends RefCounted
var claim_id: String
var text: String
var claim_kind: String            # fact/calculation/inference
var reasoning_pattern: Variant    # correlation/causation/subset_vs_total/other 或 null
var correct_label: String
var explanation: String
var key_evidence_ids: Array[String]      # 判定时必须考虑的证据（不区分支持/反对）
var related_evidence_ids: Array[String]  # 相关可关联（含 key）
```

```gdscript
class_name EvidenceDefinition
extends RefCounted
var evidence_id: String
var title: String
var source_type: String
var record_type: String           # snapshot/log/registry/handover/note（§6 枚举）
var created_at: String            # ISO 日期或日期时间
var valid_from: Variant           # null 表无限早
var valid_until: Variant          # null 表无限晚
var reliability: String
var reliability_basis: String     # 覆盖范围/依据（必填）
var is_primary: bool
var content_format: String        # text/table
var content: String
var table: Dictionary             # {columns:[], rows:[[]]}；text 时为 {}
var relations: Array              # [{claim_id, relation}] 复盘/校验用，不向玩家展示
```

```gdscript
class_name CaseDefinition
extends RefCounted
var case_id: String
var title: String
var difficulty: String
var order: int
var as_of: String
var briefing: String
var objectives: Array[String]
var fiction_note: String
var report_segments: Array        # [{type:"narration"|"claim", text?, claim_id?}]
var claims: Array[ClaimDefinition]
var evidence: Array[EvidenceDefinition]
var final_decisions: Dictionary   # {preferred_action, accepted_actions:[{action,label,description,score_weight,reason}]}
var hints: Array                  # [{hint_id,type,text}]
var scoring: Dictionary           # {evidence:{unrelated_penalty,miss_penalty}}
var debrief: Dictionary           # {knowledge_card_id, knowledge_title, knowledge_body, model_behavior_note, transfer_check, transfer_answer}
var claims_by_id: Dictionary      # 加载时构建（O(1)）
```

**约定**：`report_segments` 的 claim 片段只存 `claim_id`，正文从 `claims_by_id` 取（单一文本源，杜绝漂移）；校验拒绝 claim 片段自带 `text`。定义对象只暴露 getter、由 ContentLoader 构造（系统 §4.2 只读约定；灰盒阶段用 public var + 约定，S3 前收紧为 getter）。

## 7. 内容 schema v2

### 7.1 `content/cases/index.json`

```json
{
  "schema_version": 2,
  "cases": [
    { "case_id": "case_001", "title": "不存在的引用", "difficulty": "easy", "order": 1,
      "unlock_condition": "always", "summary": "博物馆准备发布一份关于展品 A-17 调拨的内部报告，等待调查员核查。" }
  ]
}
```

### 7.2 `content/cases/case_001.json`

见 §9（完整内容），字段结构与系统 §6.2 一致。

### 7.3 加载校验（`ContentLoader`，返回 `CaseLoadResult`，不抛异常）

完整清单（每条配一个负例 fixture）：
1. `schema_version` 必须 == 2。
2. 所有 id 唯一；`claims` 数量 3–5；`key_evidence_ids ⊆ related_evidence_ids` 且 key 非空、引用存在。
3. 12 个枚举字段合法（§6）。
4. 日期 ISO；`valid_from`/`valid_until` 都非 null 时才比较 `valid_from <= valid_until`。
5. **outdated 两条件**：每条 `correct_label == outdated` 的 claim 至少一条 key evidence 满足 `valid_until < as_of`，且没有 `valid_from <= as_of` 的新来源支持它。
6. `record_type == snapshot` 时 `valid_until` 必须非空；`valid_from > as_of` 的来源是"已公布未生效"（不参与 outdated 判定）。
7. `preferred_action` 在 `accepted_actions` 中；至少一个动作 `score_weight == 1.0`；`score_weight ∈ [0,1]`。
8. `report_segments` 中 claim 片段引用存在；每条 claim **有且仅被引用一次**（防止孤儿陈述或重复引用）；claim 片段不带 `text`。
9. 文案非空（`fiction_note`/`model_behavior_note`/`reliability_basis`/explanation）；知识解释禁含拟人化意图词（"故意/撒谎/意识/想骗/欺骗"）。
10. `content_format == table` 时 `columns` 非空、每行长度 == 列数；`text` 时 `table` 空。
11. `relations[].claim_id` 引用存在；`unlock_condition` 合法。
12. 解析用 `JSON.new().parse()` 取错误行号；数字按 float 处理。

## 8. 案件 01 内容（§9 的完整数据）— 时间线先定死

**事实时间线**：事件日 2026-11-13 晚；`as_of = 2026-11-14`。ORION 报告声称 A-17 于当晚 19:42 被移至展厅 C，援引调拨单 TR-204。

### 8.1 证据（5 条，完整字段）

| id | 标题 | 来源 | record_type | created_at | valid_from | valid_until | 可靠度 | 正文要点 |
|---|---|---|---|---|---|---|---|---|
| evidence_001 | 展品库存盘点快照 | primary_record | snapshot | 2026-11-13T18:00 | 2026-11-13T18:00 | 2026-11-13T18:00 | high | 截至 11-13 18:00 盘点，A-17 登记于一楼展厅；本快照不覆盖 18:00 后的变动 |
| evidence_002 | 展厅 C 门禁日志 | primary_record | log | 2026-11-13T20:30 | 2026-11-13T19:00 | 2026-11-13T20:00 | high | 19:00–20:00 展厅 C 有访客与工作人员正常出入；**本日志仅记录人员门禁，不记录展品搬运（展品搬运走货梯另行登记）** |

| evidence_004 | 值班人员交接记录 | internal_note | handover | 2026-11-13T21:00 | null | null | medium | 当班交接提到 A-17 需修复，未提及任何移动 |

### 8.2 陈述（3 条）

| id | 文本 | 正确标注 | key_evidence_ids | related_evidence_ids | 解释 |
|---|---|---|---|---|---|
| claim_001 | 展品 A-17 于 19:42 被移至展厅 C。 | `unverified` | evidence_001, evidence_004, evidence_005 | evidence_001, evidence_002, evidence_004, evidence_005 | 没有任何证据覆盖 19:42 的移动（快照是 18:00、门禁不记展品、交接未提、修复备注是事后），因此**无法确认**移动是否发生；但也**不能证明没发生**——缺直接证据，不是相反证据 |
| claim_002 | 此次移动由调拨单 TR-204 批准。 | `contradicted` | evidence_003 | evidence_003 | 完整登记总账（任何调拨须登记）中**不存在 TR-204**——这是虚构引用。即使"移动"本身未被证实（claim_001），"TR-204 批准"这一部分仍被完整登记否定 |
| claim_003 | 展厅 C 当晚 19:00–20:00 对访客正常开放。 | `supported` | evidence_002 | evidence_002 | 门禁日志直接支持（有访客出入） |

### 8.3 报告（`report_segments` 全文）

```
narration: "关于 11 月 13 日晚展品 A-17 的位置，经核查档案，结论如下："
claim: claim_001
narration: "该次移动已履行内部审批手续，"
claim: claim_002
narration: "展厅开放情况方面，"
claim: claim_003
narration: "综上，展品 A-17 的调拨符合内部流程，档案记录完整。"
```

claim_002 的句子（"此次移动由调拨单 TR-204 批准"）要"看起来规范"（编号 TR-204 格式正确），正是教学点。

### 8.4 最终建议

- `preferred_action`: `revise`（存在明确错误：虚构引用）。
- `accepted_actions`: `revise`（1.0，"存在虚构引用，应退回修订"）、`hold`（0.6，"谨慎，但未指出确定性错误"）、`approve_with_caveat`（0.1）、`approve`（0.0）。
- 复盘解释"为什么 revise 更优、hold 为何只拿部分分"。

### 8.5 提示（3 条，问题式引导，不剧透）

- `hint_001`（direction）："报告里的每个编号都应该能在登记里找到出处。检查一下报告提到的那个调拨单编号。"
- `hint_002`（evidence）："调拨单登记清单是完整的吗？它覆盖了哪些编号？"
- `hint_003`（concept）："记录里'不存在某个编号'和'没找到关于某事的记录'，是两种不同的证据强度。"

| INVESTIGATING | judge/link/unlink/use_hint | INVESTIGATING | 参数合法 | 覆盖式更新 |
| INVESTIGATING | all_claims_judged() 为真 | READY_TO_SUBMIT | 全判完 | 自动 |
| READY_TO_SUBMIT | judge_claim（改判）/link/unlink/use_hint | READY_TO_SUBMIT | 参数合法 | **保持 READY，允许补关联/改判/用提示** |
| READY_TO_SUBMIT | submit_final(action) | SUBMITTED | action 合法 | 首次计算并缓存 CaseResult；重复同参返回 true、异参 false，不重评分 |
| SUBMITTED | begin_debrief() | COMPLETED | — | 进度/知识卡在 GameFlow 层更新 |
| INVESTIGATING/READY_TO_SUBMIT/SUBMITTED/COMPLETED | GameFlow.reset_case() | INVESTIGATING | — | session.reset() + current_result=null（best_score 保留、completed 不回滚） |
| 任意 | end_case() | — | — | 清 session/result/case_def |

### 10.2 GameFlow API（补全，Presentation 所有变更经它）

```gdscript
var current_case_def: CaseDefinition = null
var current_session: CaseSession = null
var current_result: CaseResult = null

func start_case(id: String) -> bool        # 加载成功→构造 session→phase=BRIEFING→emit case_started
func begin_investigation() -> bool
func judge_claim(claim_id, label) -> bool  # 转发 + phase 守卫 + emit case_state_changed
func link_evidence(claim_id, evidence_id) -> bool
func unlink_evidence(claim_id, evidence_id) -> bool
func use_hint(hint_id) -> bool
func submit_final(action) -> bool          # 成功后 Scorer.score → current_result → emit case_submitted
func begin_debrief() -> bool               # 更新 PlayerProgress（知识卡/完成）+ emit case_completed
func reset_case() -> void
func end_case() -> void
```

信号：`case_started(id)` / `case_state_changed(from,to)` / `case_submitted()` / `case_completed(id)`。每个 mutation 的合法 phase、成功后 emit 哪个信号、失败返回什么，与 §10.1 逐行对齐。PlayerProgress 由 GameFlow 持有（内存），场景只读。

## 11. 评分系统（系统 §9 落地，修正版）

`Scorer.score(session, case_def) -> CaseResult`。满分 100 = 60 判定准确度 + 30 证据关联 + 10 最终建议，再减提示扣分。内部 float，最终显示 round half up。

### 11.1 判定准确度 60 — 4×4 矩阵（16 格写死）

| correct \ player | supported | contradicted | unverified | outdated |
|---|---|---|---|---|
| **supported** | 1.00 | 0.00 | 0.50 | 0.00 |
| **contradicted** | 0.00 | 1.00 | 0.50 | 0.00 |
| **unverified** | 0.00 | 0.00 | 1.00 | 0.00 |
| **outdated** | 0.00 | 0.00 | 0.50 | 1.00 |

每条 claim 满分 `60/n`，乘系数。规则：精确一致 1.00；"把缺乏证据断言成明确结论"→ 0.00；"本该是明确结论却判 unverified"→ 0.50；其余错误断言 → 0.00。

### 11.2 证据关联 30（label 门控）

每条 claim：`raw = clamp(hit - λ·min(unrelated,key_count) - μ·miss, 0, key_count)`，λ=μ=1（可被 scoring 覆盖）。**门控：`raw` 只在 `matched == true`（label 判对）的 claim 计入**。

`evidence = 30 × Σ(matched 的 raw) / Σ(全部 key_count)`，clamp [0,30]。分母 `Σkey_count` 恒 > 0（§7.3 校验）。集合运算前先去重。

### 11.3 最终建议 10

`chosen == preferred_action` → 10；否则查 accepted_actions 权重 → `10·w`；否则 0。UI 不显示权重。

### 11.4 提示扣分

每案 3 条，单局任选 1 条，使用后固定扣 5 分：`total = max(0, round(earned) - 5·hint_used)`，`hint_penalty = earned - total`，`hint_used ∈ {0,1}`。UI 明确显示"使用提示 −5 分"。

### 11.5 反刷分不变量（`test_scoring_invariants.gd` 断言）

- 满分恒等于 100（无提示）。
- **排序**：全对(100) > 2/3 正确(≈80) > 全 unverified(60) > 乱选(<60)。
- **全 unverified + 全 key 证据 + 正确动作 = 60（封顶）**，显著低于全对（证据门控后成立）。
- 使用提示后严格低于未提示（固定 −5）。
- 空 case / Σkey_count==0 → 返回零分 CaseResult 并记 Warning 日志（防御性 guard，不抛错、不崩溃结算）。

## 13. UI 设计（灰盒）

### 13.1 页面
替换 5 个占位页为真实现：`briefing`、`investigation`、`final_verdict`、`results`、`debrief`。`case_select` 做**最小可用**（读 catalog，1 张案件卡，点击 `GameFlow.start_case`）；`collection`/`settings` 仍是占位。

### 13.2 调查桌面（核心）

四区域（系统 §5.4/§11.1），节点名稳定（S3 复用）：
- 左：objectives、进度 pips（每条 claim 一个圆点，已判/未判，点击定位）、glossary 入口。
- 中：报告（`RichTextLabel` + `[url=claim_id]` 渲染 `report_segments`，claim 内联可点击聚焦）。
- 右：证据列表（证据卡：标题 + 来源 + 可靠度），点击打开证据查看器叠加层。
- 底部：当前陈述文本 + 四类判定按钮（`ClaimLabelCatalog` 定义）+ 已关联证据 + "关联证据"按钮 + **"提示"按钮**（3 条选 1 条，显示"使用后 −5"）+ **"去提交"按钮**（READY_TO_SUBMIT 时亮起）。
- **READY_TO_SUBMIT 不锁控件**：进入 READY_TO_SUBMIT 后，判定按钮、证据关联、提示按钮保持可用（可微调补关联/改判），只有点"提交最终建议"才进入 SUBMITTED 结算。
- 常驻 footer/badge："虚构案例 · 非真实模型测评"。

### 13.3 证据查看器（`CanvasLayer + PopupPanel`）
展示：标题、来源类型、created_at、valid_from/valid_until、可靠度 + `reliability_basis`、是否一手、正文/表格。**不展示 relations/related_claim_ids**。底部"关联到当前陈述"按钮 → `evidence_link_requested(evidence_id)`。

### 13.4 其他页面
- `briefing`：标题 + 背景 + objectives + `as_of` + `fiction_note` + "开始调查"。
- `final_verdict`：四个动作（`FinalActionCatalog` 描述，不显示权重）+ 提交。
- `results`：总分 + 三项分项 + 提示扣分 + **最终动作结果（对/部分/错）** + "查看复盘"CTA（**不显示逐条对错**）。
- `debrief`：逐条揭晓（玩家判断 + 玩家关联的证据链 + 正确 label + 解释）→ 知识点 + 知识卡（含 scope/caveat）→ 迁移题（选择题，先答再看参考答案）→ "返回案件列表"（无下一案时隐藏"下一案"）。

### 13.5 迁移题格式
`transfer_check = {question, options: [...], answer_index}`，交互式先答再揭晓，不计分。

### 13.6 onboarding（最小版，落回 S2）
1. 简报内嵌 2 步互动校准：一条样例陈述 + 两张证据卡，玩家先选四类之一，再显示解释。
2. 案件 01 首条 claim 引导：首次进入桌面高亮"点陈述→选判定→关联证据"三步。
3. 常驻 glossary 抽屉：四类判定 + "幻觉" + `unverified` vs `contradicted`、`outdated` vs `contradicted` 的一句话区分。
